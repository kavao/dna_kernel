## 目的

長いプロジェクトでは、会話の途中でコンテキストが薄れる。このスキルは、
**プロジェクトの現状を短くまとめ、別セッション・別エージェントが引き継げる形**にすることを目的とする。

## 要約に含める内容

### 必須

- **プロジェクトの目標**: 何を達成しようとしているか（1〜3行）
- **主要な制約**: してはいけないこと、優先順位、依存関係
- **現在の状態**: どこまで進んでいるか

### 推奨

- **アーキテクチャの決定**: なぜその構成になっているか
- **共有の規約**: 命名・フォルダ構造・フォーマットのルール
- **検証の方法**: 完了確認に使うツールやコマンド
- **次のタスク**: 続きで誰かが拾ったときに迷わない引き継ぎ情報

## 出力の形式

- **簡潔に**: 長い説明より箇条書き。読み返しやすさを優先する。
- **ファイルへ保存**: チャットに出すだけでなく `_workingspace/plans/YYYYMMDD_<topic>_plan.md` または指定パスへ保存する（`output-discipline` に従う）。
- **参照先を明記**: 詳細が別ファイルにある場合はパスをリンクする。

## よくある使い場面

- セッションの最初に「今どこにいるか」を把握するとき
- 別エージェントへ作業を引き渡すとき
- 長い作業の途中で「何をしているのか」を確認したいとき

## 短い呼び出し

ユーザーは長いテンプレートを使わず、次のような一言だけで作業計画を操作できる。

- 「計画を作って」: 同じテーマの既存計画を確認し、なければ新規作成する。
- 「TODOに追加して」: 現在の計画へ未完了タスクを追加する。
- 「残タスクを教えて」: 計画の `- [ ]` と直近ログを確認して要約する。
- 「計画を更新して」: 完了済みタスク、検証結果、次のタスクを現在の状態へ更新する。

## 作業計画ファイルの運用

- `_workingspace/plans/*.md` は複数セッション・複数PCで状態を共有するため Git 管理対象とする。
- `- [ ]` は未完了タスク、`- [x]` は完了タスクを示す。
- 状況や残タスクを尋ねられたら、`_workingspace/plans/` と `_workingspace/log/YYYYMM.md` を最初に確認する。
- ログと日記の本文はローカル専用とし、計画書だけを共有対象にする。
- 正式な変更履歴は Git 履歴とし、確定した決定・制約は `docs/` または `.rulesync/` の正本へ反映する。
- API キー、パスワード、アクセストークン、秘密鍵、個人情報を記録しない。

## エージェント向け運用

このスキルが呼ばれたら、次の順で実施する。

1. `_workingspace/plans/` と `_workingspace/log/` を確認し、現状を把握する。
2. 同じテーマの計画がある場合は、新規作成せずそのファイルを更新対象にする。
3. 要約を作り、チャットへ提示する。
4. 必要なら `_workingspace/plans/` の計画を作成または更新する。
5. 「次にすべきこと」を明確に提示する。
