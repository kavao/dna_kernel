# dna_kernel 一般リポジトリ導入性・説明構造改善計画

作成日: 2026-08-18
対象: `dna_kernel` 本体
状態: 計画
バージョン: 0.6

## 1. 目的

`dna_kernel` を、一般の開発・創作リポジトリへ組み込むための「ルール体系のカーネル」として理解・導入しやすくする。

次の5点を、人間とAIの双方が入口から把握できる状態を目標にする。

1. 既存リポジトリへ**組み込むためのもの**であること
2. 組み込むことで得られる**具体的な効用**
3. 単体ツール集ではなく、**正本・手順・生成物・証跡を持つルール体系**であること
4. Node.js等を必須にせず、**依存性を抑えて導入・運用できる**こと
5. Codex、Claude Code、Cursor、Grok Build等を行き来する際の**ツール切替コストを下げられる**こと

今回の計画は説明と構造の改善を対象とし、ルール内容そのものの大幅な増減は対象外とする。特定のLLMツールへの依存拡大も対象外とするが、Rulesync固定版が生成確認済みで標準対応するtarget（`grokcli` 等）の追加は、ツール切替コストの効用を正しく説明するための例外として扱う。根拠のない対応target追加は、この例外に含めない。

## 2. 現状確認

### 2.1 すでにあるもの

- ルートREADMEに「自己発展型ルールガバナンスを注入する最小カーネル」と記載されている。
- `manifest.md` に各ファイルの役割と導入先での配置先がある。
- `docs/ja/dna-kernel/onboarding.md` に新規作成・既存注入・本体開発の3モードがある。
- `.rulesync/` に概念ルールとAI向けスキルの正本があり、rulesyncで各ハーネス向け設定を生成する。
- `tools/kernel/` の主要ツールは標準ライブラリのみで動作し、`pyproject.toml` の依存パッケージは空である。
- RulesyncはPythonラッパー経由の固定版単体バイナリとなり、日常の生成にNode.js、npm、pnpm、Corepackを必要としない。
- `manifest.md` に「ルールだけ」「ログまで」「pre-work-checkまで」の最小セット例がある。
- `tools/kernel/user_prefs.py` と `user-locale` スキルにより、会話言語の解決順位（チャット明示 → `.dna-kernel.local.toml` → ホーム config → OS locale）とプロジェクト単位の上書きがすでにある。

### 2.2 改善が必要な点

- ルートREADMEの冒頭だけでは、導入先リポジトリへファイルを注入するプロダクトであること、対象読者、最初に選ぶ導入パターンが十分に伝わらない。
- 効果の説明が「ルールが肥大しない」「完了が曖昧にならない」などの抽象表現に寄っており、導入前後の具体的な変化と成果物が見えにくい。
- `.rulesync/`、生成されたLLM設定、`tools/kernel/`、`docs/`、`_workingspace/` の関係が、一覧としては存在するが、ルール体系の層として一望しにくい。
- 最小セットの考え方はあるものの、どのリポジトリにどのセットを選ぶか、各セットに何が含まれるかが導入手順と一体化していない。
- Python、uv、Rulesync、Node.js、ネットワークの関係が混在しており、「実行に必須」「生成・更新時だけ必要」「任意」が一目で分からない。
- AIが導入依頼を受けたときに最初に読む資料、導入プロファイルを選ぶ基準、変更前の確認、完了時の報告項目を、入口から辿れる形に整理する余地がある。
- 計画書・設計書を版数と変更履歴なしに直接書き換えており、どの回答でどこを変えたかが会話ログを遡らないと分からない。

## 3. 改善後の基本メッセージ

### 3.1 一文での位置づけ

次の趣旨を、ルートREADMEと詳細説明の冒頭で共通して伝える。

> `dna_kernel` は、既存リポジトリにコピー・統合して使う、LLM向けのルール体系カーネルです。ルールの正本、実行手順、生成された各ツール向け設定、完了確認と作業証跡を一つの運用へまとめます。

「最小カーネル」という表現は残すが、単体アプリケーションではなく、既存プロジェクトへ注入する部品群であることを直後に補足する。

### 3.2 具体的な効用

導入前後を次のように説明できる状態にする。

| 導入前に起きやすいこと | dna_kernel導入後の仕組み | 確認できる成果物 |
|---|---|---|
| AIツールごとに指示が分岐し、修正漏れが起きる | `.rulesync/` の正本から各ツール向け設定を生成する | `AGENTS.md`、`CLAUDE.md`、`.cursor/` 等 |
| 「完了した」の根拠が会話だけになる | ファイル保存、再読込、機械検査を完了条件にする | `generate --check`、テスト結果、チェック項目 |
| 作業履歴が後から書き換えられる | 査証ログを追記専用で残す | `_workingspace/log/YYYYMM.md` |
| 計画の概要と詳細チェックが食い違う | `[ ]` / `[x]` と計画検査で状態を統一する | `_workingspace/plans/*.md`、`plan_check.py` |
| 新しいPC・OSでNode環境の準備が必要になる | Python標準ライブラリと固定版Rulesyncラッパーを使う | `tools/`、`config/rulesync_toolchain.json` |
| Codex、Claude Code、Cursor、Grok Build等を行き来するたびに指示を説明し直す | 共通の正本から対応するツール向け設定を生成・同期する | `.rulesync/`、各ツール向け生成設定、target設定 |
| ツールを切り替えるたびに会話言語の希望を説明し直す | 会話言語の解決順位を共通化し、プロジェクト単位の上書きを残す | `user-locale` スキル、`.dna-kernel.local.toml`、生成された `user-locale` 副本 |
| 計画書のどの版で何を変えたか分からなくなる | ヘッダのバージョン欄と追記専用の変更履歴で状態を追跡する | `_workingspace/plans/*.md` のバージョン欄、`## 変更履歴`、`plan_check.py` |

ツール切替コストの低下は、次の作業を減らすこととして具体化する。

- 同じルールや禁止事項を、ツールごとの会話開始時に再説明する作業
- ツールごとに異なる指示ファイルを手作業で修正し、差分を追いかける作業
- 別ツールへ移ったときに、完了条件・作業履歴・計画の状態を説明し直す作業
- ツール固有の出力差によって、同じルールの適用漏れを再確認する作業
- ツールを切り替えるたびに、会話言語（日本語/英語等）の希望を毎回指定し直す作業

ただし、切替コストを下げられる範囲は、Rulesyncの対応targetまたは導入先で定めた互換入口の範囲とする。現在の標準targetは `claudecode`、`cursor`、`codexcli`、`grokcli` であり、Rulesync 15.0.1は `grokcli` で `.grok/skills/` を生成する。実際のGrok Buildがその配置を読むことは導入先で確認し、対応済み／要追加統合を正確に表示する。

効果は「AIが賢くなる」ではなく、AIを使うプロジェクトのルール・完了・履歴を再現可能にすることとして表現する。

### 3.3 対象外も明示する

- LLMやIDEそのものを提供するものではない。
- プロジェクト固有の設計・業務ルールを自動生成するものではない。
- ルールを置けばAIが必ず従うことを保証するものではない。
- すべてのOS・CPUや、すべてのLLMハーネスを無条件に保証するものではない。

対象外を併記し、過剰な期待を避ける。

## 4. ルール体系としての構造整理

### 4.1 説明する層

一般リポジトリへ組み込まれる構造を、次の5層として説明する。

```text
人間の入口・導入判断
        │
        ▼
docs/ + manifest.md + onboarding
        │  何を、どこへ、どの範囲で組み込むか
        ▼
.rulesync/rules/        概念・禁止・完了条件の正本
.rulesync/skills/       AIが実行する手順の正本
        │
        ├── rulesync ──► 各LLMツール向け生成設定
        └── tools/kernel/ ──► 機械検査・証跡・補助処理
                                      │
                                      ▼
                              _workingspace/
                              計画・ログ・日記
```

「ルールが中心で、ツールはルールを実行・検証するための補助」という関係を明示する。
同じ正本から複数のツール向け設定を作ることで、開発作業をCodex、Claude Code、Cursor等の間で切り替えても、ルール・完了条件・作業記録の再説明を最小化できることも、この構造の主要な効用として示す。

### 4.2 正本・生成物・記録の境界

次の分類を、`manifest.md` と詳細READMEで同じ表現にする。

| 区分 | 主な場所 | 扱い |
|---|---|---|
| 正本 | `.rulesync/rules/`、`.rulesync/skills/`、`rulesync.jsonc` | 人が編集し、変更の起点にする |
| 生成物 | `AGENTS.md`、`CLAUDE.md`、`.cursor/` 等 | 直接編集せず、正本から再生成する |
| 実働補助 | `tools/kernel/`、`tools/rulesync.py` | 正本に定めた確認・生成を実行する |
| 人間向け説明 | `docs/`、`manifest.md` | 導入判断と操作を説明する |
| プロジェクト記録 | `_workingspace/plans/`、`_workingspace/log/`、`_workingspace/diary/` | 導入先の作業事実を残す |

### 4.3 導入プロファイル

導入先が必要以上に取り込まなくてよいよう、次のプロファイルを導入手順とmanifestに整理する。

| プロファイル | 目的 | 主な構成 |
|---|---|---|
| Rule-only | まずルールの正本と各AI設定を統一する | `.rulesync/rules/`、`rulesync.jsonc`、Rulesyncラッパー、生成設定 |
| Governance | 完了判定と作業証跡まで統一する | Rule-only + `output-discipline`、`plan-design-check`、`workspace-audit-log`、`_workingspace/` |
| Full | 導入判定・ロケール・補助処理まで利用する | Governance + `project-onboarding`、`user-locale`、必要な補助スキル・ツール |

プロファイルは最初から別配布物へ分割せず、まず既存ファイルの対応表とコピー対象一覧として整理する。重複した正本を増やす必要が生じた場合だけ、後続計画で配布単位を再検討する。

### 4.4 計画書・設計書のバージョンと変更履歴

計画書・設計書の版と変更点を、会話ログを遡らずに文書単体で追えるよう、次の構造を定量化する。

- ヘッダ（作成日・対象・状態の並び）に `バージョン: MAJOR.MINOR` を置く。MAJORは目的・対象の変更、MINORは項目の追加・修正・レビュー反映を指す。
- 文書末尾、`## 進捗` の直前に `## 変更履歴` を置き、`日付 / バージョン / 変更内容` の表で管理する。査証ログと同じ**追記専用**の原則とし、既存行の削除・上書き・並べ替えは行わない。
- 変更のたびに、ヘッダの `バージョン` と `## 変更履歴` 最終行のバージョンを一致させる。
- `skills/plan-design-check/SKILL.md` の機械検査に、バージョン欄の存在・形式、`## 変更履歴` の存在、ヘッダと履歴最終行の一致を含める。既存行が変更されていないことまでは、当面は目視レビューで担保し、機械検査の対象は新規追記の形式に限定する。

## 5. 依存性の説明方針

「依存性が低い」と「依存性がない」を混同しないよう、次の表を入口へ掲載する。

| 項目 | 扱い | 説明 |
|---|---|---|
| Python | 必須の基盤 | `>=3.11`。主要ツールは標準ライブラリのみで動作する |
| uv | 任意の実行補助 | `uv run` を推奨例にするが、標準ライブラリのツールは `python` でも実行できる |
| Node.js / npm / pnpm / Corepack | 不要 | Rulesyncの日常運用では要求しない |
| Rulesync単体バイナリ | 生成・更新時に必要 | Pythonラッパーが固定版を取得・検証し、`.tools/` にキャッシュする |
| ネットワーク | 初回取得・版更新時に必要 | 取得後の通常の生成・検査はキャッシュを利用する |
| LLMハーネス | 利用先に応じて選択 | `rulesync.jsonc` のtargetsに必要なものだけ指定する |

併せて、次の2つの運用モードを区別する。

- **利用者モード**: 生成済み設定と既存ルールを使う。PythonやRulesyncの操作頻度を抑えられる。
- **保守者モード**: 正本を変更してRulesync生成・check・テストを行う。Pythonが必要で、Rulesyncの初回取得時にはネットワークを使う。

## 6. AI向け導入体験

AIが一般リポジトリへ導入するときの標準読込順と確認内容を固定する。

1. `README` またはユーザーの導入依頼から、dna_kernel導入の意図を確認する。
2. `manifest.md` で構成要素と導入先を確認する。
3. `.rulesync/skills/project-onboarding/SKILL.md` で新規作成・既存注入を判定する。
4. 既存のREADME、docs、tools、`.rulesync/`、`rulesync.jsonc`、`.gitignore`、`.dna-kernel.local.toml` を調査する。
5. 会話言語の解決順位（チャット明示 → local → ホーム config → OS locale）を確認し、`.dna-kernel.local.toml` の追加要否を提示する。
6. Rule-only / Governance / Full のどれを使うかを提示し、変更前に了承を得る。
7. 既存READMEを守り、正本・生成物・ローカル記録を分けて導入する。
8. dry-run、生成、check、必要なテストと監査ログを実行する。
9. 追加ファイル、変更ファイル、依存性、未実施確認を報告する。

AI向けスキルには、上記の読込順、プロファイル選択、確認前の停止条件、完了報告の最小項目を明示する。プロジェクト固有の概要を推測して書かない既存方針は維持する。

## 9. 受け入れ条件

- GitHubの入口だけで、dna_kernelが一般リポジトリへ注入するルール体系であることが分かる。
- 少なくとも5つの具体的な効用が、導入後に確認できる成果物と対になって説明されている。
- Codex、Claude Code、Cursor等の間を行き来する際に、指示の再説明・設定同期・状態引継ぎのコストを下げられることが、共通正本と生成設定の関係で説明されている。
- Grok Build等の候補ツールについて、Rulesyncの `grokcli` 生成対応と、実際のGrok Build読み込み確認の区別が正確に表示されている。
- `.rulesync/` → Rulesync生成物 → `tools/kernel/` → `_workingspace/` の関係を一つの構造図と表で説明できる。
- Rule-only / Governance / Full の選択基準とコピー対象が分かる。
- Python `>=3.11`、標準ライブラリ中心、uv任意、Node不要、Rulesync初回取得時のネットワーク要件を正確に説明している。
- 人間が導入を開始する手順と、AIが導入依頼を受けたときの読込順・確認手順が一致している。
- 会話言語の解決順位とプロジェクト上書き方法が、効用説明とAI向け導入体験の両方に反映されている。
- 計画書・設計書にヘッダのバージョンと追記専用の `## 変更履歴` があり、`plan_check.py` で機械検査できる。
- 既存README、既存設定、指定された注入先ルートを尊重する制約が維持されている。
- 日英docsとRulesync生成物が同期し、`generate --check`、`plan_check.py`、テストが終了コード0になる。
- 変更事実と残課題が査証ログに追記されている。

## 10. リスクと判断

- 「最小カーネル」を強調しすぎると、単なる小さなツール集に見える。入口では「最小で導入できるルール体系」と補足する。
- 「依存なし」と断定するとPython、初回ネットワーク、Rulesync単体バイナリの条件を隠すことになる。「主要ツールは外部Pythonパッケージ依存なし」と表現する。
- 導入プロファイルを増やしすぎると選択に迷うため、最初は3種類に固定し、実際の導入で不要な分岐を削る。
- `manifest.md` とREADMEに同じ説明を全文複製すると、再び齟齬が生じる。READMEは判断、manifestは配置、docsは手順という役割に分ける。
- AI向けスキルの読込順を厳密にしすぎると、既存プロジェクトの多様な構成に適用しにくい。必須確認と推奨確認を分ける。
- 生成済み設定をコミットするかどうかは導入先の運用差があるため、正本・生成物・キャッシュの扱いをプロファイルごとに明記する。
